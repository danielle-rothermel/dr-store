The dr-store storage contracts

A reference for the terms and guarantees that bind dr-store.

This vocabulary defines the append-only content-addressed Object Store and the Document Directory: their terms, guarantees, scope, and mappings to the names exported by dr_store.

Object Store Terms

TermDefinition
RecordOne complete stored value accepted by dr-serialize's frozen Canonical JSON profile, carrying every field the caller means to persist. It is stored and returned as the canonical JSON-equivalent value, whose observable mapping order may differ from the input.
SchemaA declared name that labels the shape of a record. It is opaque to the store — a string the caller owns — and it partitions stored content so the same bytes filed under two names remain distinct.
Canonical JSONThe single deterministic UTF-8 JSON text of a value admitted by dr-serialize's frozen Canonical JSON Text profile. The profile defines both the permitted values and their rendering; dr-store never derives a second dialect of its own.
HashDeterministic fixed-length value computed by a declared algorithm over exact declared input bytes. dr-store implements the content hash specialization over canonical JSON.
KeyAn opaque caller-owned string naming a place in the binding table. Its meaning belongs entirely to the caller; the store never parses or interprets it.
BindingA single association from a key to one object reference. Once written it is never replaced, cleared, or superseded.
Idempotent ReplayA write whose incoming value is identical to the value already stored at the same place: no new content is created and the existing stored value is unchanged.
ConflictA write whose incoming value differs from the value already stored at the same place; it is a typed outcome that leaves the existing stored value unchanged.
Append-OnlyThe property that stored content is only ever added, never mutated or removed. No operation in this contract replaces or deletes an existing record or binding.
Compare-and-SetThe atomic write in which a value is stored only when its place is empty; an occupied place is left unchanged and its existing row is returned. It is the storage primitive each append-only table rests on, provided by the backend.
Content HashThe full 64-character lowercase SHA-256 hash of the canonical JSON of a complete stored record, addressing that record's content.
Object ReferenceThe typed content-addressed handle pairing a declared schema with the full content hash of a record. It resolves exactly one immutable stored record, and both parts are validated at construction so an ill-formed reference can never enter the store.
Object StoreThe authoritative append-only mapping from an object reference to the exact immutable record it addresses, plus the binding table from keys to references. It owns every semantic rule of this contract and delegates only atomic storage operations to a backend.
Immutable PutThe single stored association between one complete record and its schema-typed object reference, established once and never overwritten. A verified value at an absent place is stored, an identical value is an idempotent replay, and differing content at the same place is a conflict.
Verified GetAn object reference resolved to the exact immutable record it addresses, with the content hash and the declared schema confirmed against the stored bytes on every read.
Atomic Key-to-Reference BindingThe single generic compare-and-set that writes one binding: an unbound key binds; the same object reference is an idempotent replay; a different reference is a conflict that preserves the existing winner. No overwrite, clear, or rebind path is exposed.
BackendThe backend-neutral contract supplying atomic compare-and-set primitives for the two append-only tables, plus point reads. Persistence is implementation-specific: MemoryBackend is process-local, while SqliteBackend persists data for cross-process use. The backend stores canonical JSON text unchanged; hashing, verification, idempotency, and conflict typing live above it in the object store.

Object Store Guarantees

Stored Content Is Never Overwritten. Every write is append-only: an absent place accepts a verified value, an identical value replays as idempotent success, and any differing value is a typed conflict that preserves the existing value untouched.
  • Computes the full content hash — a lowercase 64-character SHA-256 value over canonical JSON — entirely through the serialization layer, inventing no second canonicalization.
  • Validates every object reference at construction, so a reference with an empty schema or a malformed content hash can never enter the store.
  • Stores one complete record per immutable put: an absent (schema, content hash) object reference accepts the verified value atomically; the identical canonical value is an idempotent replay; a differing value at the same object reference is a conflict.
  • Recomputes and verifies the content hash and the declared schema on every verified get — a read never trusts stored bytes unchecked.
  • Fails with a typed error on every read fault: missing content, content filed under a different schema, and stored bytes that no longer hash to their reference (corruption, including unparseable content) each raise a distinct exception.
  • Binds a key to exactly one object reference through atomic key-to-reference binding: unbound binds, the same reference replays, a different reference conflicts and preserves the existing winner.
  • Exposes no overwrite, clear, or rebind path — the store is append-only for both records and bindings.
  • A content hash is not an identity hash: it covers the complete stored record, not a caller-selected identity subset.
  • The backend supplies only atomic compare-and-set primitives and point reads. MemoryBackend is process-local; SqliteBackend persists data for cross-process use.
  • The contract is domain-neutral: no workflow, retry, campaign, or other domain concept appears anywhere in it.

Object Store: In vs. Out of Scope

In scopeOut of scope

  • Typed object reference construction
  • Immutable put of complete records
  • Verified get with per-read recomputation
  • Atomic key-to-reference binding
  • Interchangeable backends
  • Typed storage errors
  • Canonical JSON rendering and hash algorithms
  • Identity hashing over a caller-selected subset

Object Store: Exported Names

Each row maps a term of the object storage contract, or a group of its supporting exports, to names in dr_store.__all__; the Document Directory section carries its own table for the rest. Every exported name appears exactly once across the two tables; there are no aliases or alternate spellings. The terms record, schema, canonical JSON, hash, key, binding, idempotent replay, conflict, append-only, and compare-and-set name concepts rather than exports, so they have no row.

TermExported namesNote
Content Hash compute_content_hash, is_content_hash, CONTENT_HASH_LENGTH compute_content_hash validates a record and returns its content hash; is_content_hash tests a string for the 64-character lowercase hex shape counted by CONTENT_HASH_LENGTH.
Object Reference ObjectReference, ReferenceValidationError Construction itself validates: an empty schema or malformed content hash raises ReferenceValidationError. The ObjectReference.for_record and verify_record methods build and check a reference against a record.
Object Store ObjectStore The whole public contract over a backend. Its resolve method is the one read-only convenience over the binding table, returning the bound object reference or None.
Immutable Put PutStatus, ObjectConflictError The ObjectStore.put method returns a reference and a PutStatus of STORED or IDEMPOTENT; a conflict is not a status but raises ObjectConflictError, preserving the stored value.
Verified Get ObjectNotFoundError, SchemaMismatchError, ContentHashMismatchError The ObjectStore.get method raises ObjectNotFoundError when nothing resolves, SchemaMismatchError when content is filed under a different schema, and ContentHashMismatchError when stored bytes no longer hash to their reference. ContentHashMismatchError is also raised by direct ObjectReference.verify_record checks.
Atomic Key-to-Reference Binding BindStatus, BindingConflictError The ObjectStore.bind method returns a BindStatus of BOUND or IDEMPOTENT; a different-reference conflict raises BindingConflictError, which carries the preserved existing winner.
Backend Backend, MemoryBackend, SqliteBackend, PutOutcome, BindOutcome Backend is the neutral protocol; MemoryBackend and SqliteBackend are the two interchangeable implementations. PutOutcome and BindOutcome are the backend-level results a compare-and-set returns, distinct from the caller-facing PutStatus/BindStatus.
Storage errors StoreError The base class for Object Store contract failures. Document Directory failures derive separately from DocumentDirectoryError.

Document Directory

The Document Directory carries one canonical-JSON manifest published by same-directory replacement plus streamed binary sidecars. Its vocabulary is disjoint from the Object Store contract: no term here is an object reference, a content hash, or a binding.

TermDefinition
Document DirectoryOne allocated directory intended for caller-coordinated single-writer use, with one manifest and zero or more sidecars. It is created under a caller-owned root with a generated name; dr-store does not lock or otherwise enforce the single-writer policy.
ManifestThe single canonical JSON document published by same-directory replacement for a document directory, and the source of truth about every sidecar it describes — meaning, stored segment lengths, and sidecar digest. Its payload is opaque to dr-store, which never reads a field out of it.
SidecarA raw-bytes artifact written incrementally beside the manifest, possibly truncated under caps the caller supplies, and never self-describing: nothing about a sidecar's meaning or completeness can be recovered from the sidecar alone.
Sidecar DigestThe full 64-character lowercase SHA-256 hash of a sidecar's stored bytes, after truncation. It is not a content hash: its input is raw bytes, not the canonical JSON of a record.
Manifest Visibility Depends on Filesystem Semantics. After writing and flushing complete contents, publication replaces the manifest in the same directory. All-or-nothing visibility depends on the filesystem honoring atomic same-directory replacement; network, synchronized, or other filesystems whose rename semantics are not established are outside current evidence. The directory flush does not promise power-loss durability.
  • Allocates a statistically unique document directory name of the form <prefix>-<utc-timestamp>-<uuid4>. There is no retry loop: a generated-name collision is a typed error, never a silent reuse.
  • Validates prefixes, manifest names, and sidecar names as single path segments — no separator, no NUL byte, never . or ... This prevents lexical traversal syntax only: Manifest reads and Sidecar creation and writes follow existing final-component symlinks, so callers must control and trust the directory contents.
  • Publishes a manifest by writing and flushing the complete canonical JSON in a temp file, replacing the manifest in the same directory, and flushing the directory. Atomic visibility has the filesystem dependency stated above. A final directory-flush failure raises even though the replacement may already be visible.
  • Computes the sidecar digest incrementally. Finalization flushes the sidecar descriptor before returning its SidecarSummary, but does not flush the containing directory entry. Callers control when or whether any manifest is published; no ordering with an arbitrary publication is enforced.
  • Reports produced and dropped byte counts alongside the stored segment lengths, so a truncated sidecar states exactly what it discarded.
  • Verifies a read-back manifest as strict and canonical JSON. Sidecar verification is the no-follow path: it pins the opened Document Directory and regular child descriptors while checking a caller-supplied total length and sidecar digest. Faults are typed, with originating OS or decoding exceptions preserved when present.
  • The component owns no lifecycle, manifest schema, or retention policy. Payload fields, cap computation, and output-draining policy belong to the caller.
TermExported namesNote
Document Directory DocumentDirectory, AllocationError The DocumentDirectory.allocate class method creates the directory; a lexically invalid name or a failed mkdir raises AllocationError. open_sidecar opens a sidecar beside the manifest.
Manifest ManifestPublishError, ManifestReadError The DocumentDirectory.publish method replaces the manifest in the same directory and flushes it; a non-strict payload or a failed write, replace, or flush raises ManifestPublishError. The DocumentDirectory.read_manifest class method returns the stored payload; a lexically invalid manifest name or a missing, unreadable, malformed, non-strict, or non-canonical document raises ManifestReadError.
Sidecar SidecarWriter, SidecarSummary SidecarWriter.write offers bytes under the caps and finalize flushes and returns the frozen SidecarSummary — stored segment lengths, produced, dropped, and the sidecar digest. dr-store never serializes a summary.
Sidecar Digest SidecarVerificationError The DocumentDirectory.verify_sidecar instance method uses no-follow, pinned descriptors to verify a regular direct child of that directory against a caller-supplied digest and total segment length; a length or digest disagreement, or an unreadable file, raises SidecarVerificationError.
Document Directory errors DocumentDirectoryError The base class every Document Directory failure derives from, independent of StoreError so a caller can branch on one component without catching the other.
